# Sphero RVR official API / protocol capability matrix

This matrix inventories the official local-control RVR surface used for parity planning. It is discovery-only; no protocol implementation changes are made by this card.

See `docs/rvr_api_gap_report.md` for the follow-up audit that maps this matrix to the current command builders, parsers, driver methods, dispatcher behavior, ROS node surfaces, tests, and exact remaining gaps.

See `docs/rvr_notification_events.md` for the dedicated unsolicited notification/event audit that defines enable commands, expected packet fields, parser shapes, cache/topic behavior, fake transport fixtures, and safety implications before dispatcher implementation.

## Sources and interpretation

- Primary SDK snapshot: `sphero-sdk==0.3.4.post2`.
- Public async API: `sphero_sdk.asyncio.client.toys.sphero_rvr_async.SpheroRvrAsync`.
- Generated command/protocol modules inspected:
  - `sphero_sdk.common.commands.api_and_shell` / `0x10-api_and_shell.json`
  - `sphero_sdk.common.commands.system_info` / `0x11-system_info.json`
  - `sphero_sdk.common.commands.power` / `0x13-power.json`
  - `sphero_sdk.common.commands.drive` / `0x16-driving.json`
  - `sphero_sdk.common.commands.sensor` / `0x18-sensors.json`
  - `sphero_sdk.common.commands.connection` / `0x19-peer_connection.json`
  - `sphero_sdk.common.commands.io` / `0x1A-user_io.json`
- Device IDs in the official SDK:
  - API/shell `0x10`
  - system info `0x11`
  - power `0x13`
  - drive `0x16`
  - sensor `0x18`
  - connection `0x19`
  - user I/O `0x1A`
- SDK target convention: `BT = 1`, `MCU = 2`; several methods accept either target explicitly.
- Request/response classification is inferred from generated command dictionaries: commands with `outputs` are request/response, notification registration methods are event subscriptions, the rest are fire-and-forget/error-only in the current protocol layer.
- Current repo support is based on `src/sphero_rvr_core/commands.py`, `src/sphero_rvr_core/driver.py`, `src/sphero_rvr_driver/rvr_node.py`, and tests present when this file was written.

## Status vocabulary

- `core-implemented`: core driver currently has a method and packet/response coverage.
- `core-planned`: should be implemented in core parity work.
- `core-only`: useful in core but not a routine ROS graph surface.
- `ros-exposed`: should be or already is bridged into ROS topics/services/subscriptions.
- `ros-intentionally-omitted`: deliberately kept out of ROS even if core supports it.
- `needs-protocol-research`: official surface exists but packet behavior/response/event semantics need extra confirmation before implementation.
- `omitted-unsafe-or-admin`: valid but too risky/admin-ish for routine driver exposure.

## Test status vocabulary

Every capability row must classify its current validation state with one or more explicit tokens:

- `builder-test`: packet builder payload/target/DID/CID coverage exists.
- `parser-test`: response or event payload parser coverage exists.
- `driver-test`: async `RVRDriver` fake-transport coverage exists.
- `notification-test`: unsolicited dispatcher/subscription callback coverage exists.
- `ros-exposure-test`: ROS node/config/safe-surface coverage exists without importing ROS on development hosts.
- `fake-transport-test`: validation is no-hardware/fake transport only.
- `documented-omission`: remaining gap or unsafe/admin/ROS omission is deliberately documented in this matrix and policy docs.

## Cross-cutting gaps found during inventory

1. **Notification routing is the largest architectural gap.** Official event methods exist for battery voltage state, sleep, gyro max, motor stall/fault, color detection, streaming data, IR receive, and motor thermal protection. The current dispatcher handles request/response and sends, but there is no typed notification subscription layer yet.
2. **Infrared broadcast/send protocol shape conflicts with the official SDK.** The official public SDK uses sensor DID `0x18` for send/broadcast/stop-broadcast and a five-strength payload for `send_infrared_message`; the current repo uses `DID_IR = 0x1C` plus shorter payloads for some of these. Marked `needs-protocol-research` for implementation follow-up.
3. **Color current reading semantics likely conflict.** Official docs state `get_current_detected_color_reading()` sends no direct output and instead produces `color_detection_notify`; current repo parses it as direct request/response. Needs confirmation before parity implementation.
4. **Temperature API shape differs.** Official SDK exposes per-motor `get_motor_temperature(motor_index)` at CID `0x42`; current repo has a convenience `get_temperature()` using payload `[4,5]` and parsing two motor values. Needs reconciliation.
5. **Several current implementations are useful partials, not full parity.** Battery voltage fixes `reading_type=0`; LED control exposes convenience RGB/group methods rather than the full mask/vector payload; firmware version maps only main application version.

## Suggested ROS exposure summary

- Already exposed: `cmd_vel`, `stop`, `estop`, `clear_estop`, battery percentage/voltage topic, motor temperature topics, driver diagnostics.
- Good ROS candidates after core parity: reset yaw/locator services, battery state diagnostics, board/SKU/firmware diagnostics, ambient/RGBC typed sensor topics, fault/stall/thermal/sleep/color event topics once notification routing exists.
- Keep core-only/omitted by default: raw motors, sleep, stats ID, arbitrary echo, palette persistence, low-level streaming bytes, IR autonomous follow/evade/broadcast controls, calibration/admin-like commands.
